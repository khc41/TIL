### 11장. 스트림 처리
- 일괄 처리의 출력은 파생 데이터고 입력을 사전에 알려진 유한한 크기로 한정한다. 하지만, 데이터셋은 절대 완료될 수 없으므로 인위적으로 일정 기간씩 데이터 청크를 나눠야 하는데 이를 매 초가 끝나는 시점에 처리하거나 이벤트가 발생할 때마다 처리하는 것이 스트림 처리의 기본 개념이다.

#### 이벤트 스트림 전송
- 스트림 처리는 입력이 이벤트라고 하는 특정 시점에 일어난 사건에 대한 세부 사항을 포함하는 작고 독립된 불변 객체이다.
- 이벤트는 텍스트 문자열이나 JSON 또는 이진 형태 등으로 부호화 되고 파일에 덧붙이거나 관계형 테이블에 삽ㅇ비하거나 네트워크를 통해 전송하는 등의 작업을 할 수 있다.
- 이벤트는 한번 만들면 복수의 소비자가 처리할 수 있다.
- 이론상으론 파일이나 데이터베이스를 중간에 끼는 폴링 형태와 비슷하지만, 지연 시간이 낮으면서 지속해서 처리하는 방식을 지향할 때 데이터스토어를 용도에 맞게 설계하지 않았다면 폴링 방식은 비용이 크다.

##### 메시징 시스템
- 새로운 이벤트에 대해 소비자에게 알려주려고 쓰이는 일반적인 방식으로 생산자와 소비자 사이에 유닉스 파이프나 TCP 연결과 같은 직접 통신 채널을 사용하는 방법이다.
- 발행 / 구독 모델은 여러 시스템들이 다양한 접근법을 사용한다.
  - 생산자가 소비자가 메시지를 처리하는 속도보다 빠르게 메시지를 전송한다면
    - 메시지를 버리거나 큐에 메시지를 버퍼링하거나 배압을 적용한다.
  - 노드가 죽거나 일시적으로 오프라인이 된다면 손실되는 메시지가 있을까?
    - 지속성을 갖추려면 디스크에 기록하거나 복제본을 생성하거나 둘 다 해야한다.
- 메시지의 유실을 허용할지 말지는 애플리케이션에 따라 상당히 다르다
  - 주기적으로 전송되는 센서 판독값과 지표는 가끔 누락되더라도 큰 문제가 없지만 너무 많이 누락된다면 지표가 정확하지 않다는 것을 즉시 인식하기 어려워 메시지를 신뢰성 있게 전송하는 일은 매우 중요하다.
- **생산자에서 소비자로 메시지를 직접 전달하기**
  - UDP 멀티캐스트는 낮은 지연이 필수인 주식 시장과 같은 금융 산업에서 널리 사용된다. UDP 자체는 신뢰성이 낮아도 애플리케이션 단의 프로토콜은 읽어버린 패킷을 복구할 수 있다.
  - ZeroMQ 같은 브로커가 필요없는 메시징 라이브러리와 나노메시지는 TCP 또는 IP 멀티캐스트 상에서 발행/구독 메시징을 구현한다.
  - 소비자가 네트워크에 서비스를 노출하면 생산자는 직접 HTTP나 RPC 요청을 직접 보낼 수 있다. 
  - 직접 메시징 시스템은 설계 상황에선 잘 동작하지만 메시지가 유실될 수 있는 가능성을 고려해 애플리케이션 코드를 작성해야 한다.
  - 소비자가 오프라인이면 전송된 메시지를 잃어버릴 수 있고, 생산자 장비가 죽어버리면 재시도하려고 했던 메시지 버퍼를 잃어버릴 수 있다.
- **메시지 브로커**
  - 메시지 브로커는 근본적으로 메시지 스트림을 처리하는 데 최적화된 데이터베이스의 일종이다.
  - 브로커에 데이터가 모이기 때문에 이 시스템은 클라이언트의 상태 변경에 쉽게 대처할 수 있다.
  - 메시지를 메모리에만 저장하거나 디스크에 기록하는 등 다양한 방식으로 구현할 수 있다.
  - 소비 속도가 느린 소비자가 있으면 일반적으로 브로커는 큐가 제한 없이 계속 늘어나게 한다.
  - 큐 대기를 하면 소비자는 일반적으로 비동기로 동작한다.
- **메시지 브로커와 데이터베이스의 비교**
  - 데이터베이스는 명시적으로 데이터가 삭제될 때까지 데이터를 보관하는 반면, 메시지 브로커는 대부분 소비자에게 데이터 배달이 성공할 경우 자동으로 메시지를 삭제한다.
  - 메시지 브로커는 대부분 메시지를 빨리 지우기 때문에 작업 집합이 상당히 작다고 가정하고 소비자가 느려 많은 메시지를 버퍼링 해야한다면 개별 메시지 처리 시간이 길어지고 전체 처리량이 저하된다.
  - 데이터베이스는 보조 색인을 지원하고 검색을 위한 다양한 방법을 지원하는 반면 메시지 브로커는 특정 패턴과 부합하는 토픽의 부분 집합을 구독하는 방식을 지원한다.
  - 데이터베이스에 질의할 때 그 결과는 일반적으로 질의 시점의 데이터 스냅숏을 기준으로 해서 데이터가 변해도 유효하지 않은 것을 알 수 없지만 반대로 메시지 브로커는 임의 질의를 지원하지 않지만 데이터가 변하면 클라이언트에게 알려준다.
- **복수 소비자**
  - 로드 밸런싱
    - 각 메시지는 소비자 중 하나로 전달된다. 소비자는 해당 토픽의 메시지를 처리하는 작업을 공유하고 메시지 처리하는 비용이 비싸서 처리를 병렬화할 때 유용하다.
  - 팬아웃
    - 각 메시지는 모든 소비자에게 전달된다. 동일한 메시지를 서로 간섭 없이 청취할 수 있고 같은 입력 파일을 읽어 여러 다른 일괄 처리 작업에서 사용하는 것과 동일하다.
- **확인 응답과 재전송**
  - 소비자는 언제라도 장애가 발생할 수 있어 메시지를 잃어버리지 않기 위해 브로커는 확인 응답을 사용한다.
  - 브로커가 확인 응답을 받기 전에 클라이언트로의 연결이 닫히거나 타임아웃되면 브로커는 메시지가 처리되지 않았다고 가정하고 다른 소비자에게 다시 전송한다.
  - 이런 재전송 행위는 메시지 순서에 영향을 미치는데, 부하 균형 분산과 메시지 재전송을 조합하면 필연적으로 메시지 순서가 변경된다. 소비자마다 독립된 큐를 사용하면 문제를 피할 수 있다.
  - 메시지가 서로 독립이라면 순서가 바뀌는 것은 문제가 되지 않지만, 메시지 간 인과성이 있다면 매우 중요한 문제다.

##### 파티셔닝된 로그
- 네트워크 상 패킷을 전송하거나 네트워크 서비스에 요청하는 작업은 일시적 연산이므로 이미 받은 메시지를 복구할 수 없어 소비자를 다시 실행해도 동일한 결과를 받지 못한다.
- 메시징 시스템에 새로운 소비자를 추가함녀 소비자를 등록한 시점 이후에 전송된 메시지부터 받기 시작해서 이전 메시지는 복구할 수 없지만, 데이터베이스의 지속성 있는 저장 방법과 메시징 시스템의 지연 시간이 짧은 알림 기능을 조합한 것이 로그 기반 메시지 브로커의 기본 아이디어이다.
- **로그를 사용한 메시지 저장소**
  - 로그는 단순히 디스크에 저장된 추가 전용 레코드의 연속인데 브로커를 구현할 때 같은 구조를 사용해 생산자가 보낸 메시지는 로그 끝에 추가하고 소비자는 로그를 순차적으로 읽어 메시지를 받는다.
  - 디스크 하나를 쓸 때보다 처리량을 높이기 위해 로그를 파티셔닝 하는 방법이 있는데, 각 파티션은 다른 파티션과 독립적으로 읽고 쓰기가 가능한 분리된 로그가 된다. 토픽과 같은 형식의 메시지를 전달하는 파티션들의 그룹으로 정의한다.
  - 각 파티션 내에서 브로커는 모든 메시지에 오프셋이라고 부르는 단조 증가하는 순번을 부여한다. 파티션이 추가 전용이고 따라서 파티션 내 전체 메시지는 전체 순서가 있기 때문에 순번을 부여하는 것은 타당하다.
  - 모든 메시지를 디스크에 저장하지만 여러 장비에 메시지를 파티셔닝해 초당 수백만 개의 메시지를 처리할 수 있고 메시지를 복제함으로써 장애에 대비할 수 있다.
- **로그 방식과 전통적인 메시징 방식의 비교**
  - 로그 기반 접근법은 소비자가 서로 영향 없이 독립적으로 로그를 읽을 수 있고 메시지를 읽어도 로그에서 삭제되지 않기 때문에 팬 아웃 메시징 방식을 제공한다.
  - 각 클라이언트는 할당된 파티션의 메시지를 모두 소비한다. 소비자에 로그 파티션이 할당되면 소비자는 단일 스레드로 파티션에서 순차적으로 메시지를 읽는데 이런 방식의 로드 밸런싱은 불이익이 있다.
    - 토픽 하나를 소비하는 작업을 공유하는 노드 수는 많아야 해당 토픽의 로그 파티션 수로 제한된다.
    - 특정 메시지 처리가 느리면 파티션 내 후속 메시지 처리가 지연된다.
- **소비자 오프셋**
  - 브로커는 모든 개별 메시지마다 보내는 확인 응답을 추적할 필요 없이 주기적으로 소비자 오프셋을 기록하면 된다. 이는 추적 오버헤드가 감소하고 일괄 처리와 파이프라이닝을 수행할 수 있는 기회를 제공해 로그 기반 시스템의 처리량을 늘리는 데 도움을 준다.
  - 메시지 오프셋은 단일 리더 데이터베이스 복제에서 널리 쓰는 로그 순차 번호와 상당히 유사하다.
  - 소비자 노드에 장애가 발생하면 소비자 그룹 내 다른 노드에 장애가 발생한 소비자의 파티션을 할당하고 마지막 기록된 오프셋부터 메시지를 처리하기 시작한다. 이때 아직 오프셋을 기록하지 못한 메시지가 있다면 이 메시지는 재시작할 때 두 번 처리된다.
- **디스크 공간 사용**
  - 로그를 계속 추가한다면 결국 디스크 공간을 전부 사용하게 된다. 디스크 공간을 재사용하기 위해 로그를 여러 조각으로 나누고 가끔 오래된 조각을 삭제하거나 보관 저장소로 이동한다.
  - 소비자 처리 속도가 느려 생산되는 속도를 따라잡지 못하면 소비자 오프셋이 이미 삭제한 조각을 가리킬 수도 있다. 결과적으로 로그는 크기가 제한된 버퍼로 구현하고 버퍼가 가득 차면 오래된 메시지 순서대로 버린다. 이를 원형 버퍼 또는 링 버퍼라고 한다.
  - 메시지 보관 기관과 관계없이 모든 메시지를 디스크에 기록하기 때문에 로그 처리량은 일정하다. 이는 메시지를 메모리에 유지하고 큐가 너무 커질 때만 디스크에 기록하는 메시징 시스템과는 반대다.
- **소비자가 생산자를 따라갈 수 없을 때**
  - 메시지 버리기, 버퍼링, 배압 적용하기가 있다.
  - 소비자가 로그의 헤드로부터 얼마나 떨어졌는지 모니터링하면 눈에 띄게 뒤쳐지는 경우를 경고할 수 있다. 버퍼가 커질 수록 메시지를 잃기 전에 따라 잡을 시간을 충분히 벌 수 있다.
  - 어떤 소비자가 메시지를 잃기 시작해도 해당 소비자만 영향을 받기 때문에 프로덕션 서비스에 영향을 줄 우려가 없어서 운영상 이점이 있다.
- **오래된 메시지 재생**
  - 로그 기반 메시지 브로커에서 메시지를 소비하는 것은 파일을 읽는 작업과 더 유사한데 로그를 변화시키지 않는 읽기 전용 연산이기 때문이다.
  - 소비자 오프셋은 소비자 관리 아래에 있으므로 필요하다면 쉽게 조작할 수 있다. 이 점은 일괄 처리와 유사한 측면인데 변환 처리를 반복해도 입력 데이터에 영향을 전혀 주지 않고 파생 데이터를 만들기 때문이다.

#### 데이터베이스와 스트림
- 로그 기반 브로커는 데이터베이스에서 아이디어를 얻어 메시징에 적용하는 데 성공했는데 그 반대인 메시징과 스트림에서 아이디어를 가져와 데이터베이스에 적용할 수 있다.
- 이벤트는 특정 시점에 발생한 사건을 기록한 레코드이므로 데이터베이스와 스트림 사이의 연결점이 단지 디스크에 로그를 저장하는 물리적 저장소 이상이라는 점을 알 수 있다.
- 복제 로그는 데이터베이스 기록 이벤트의 스트림이다.

##### 시스템 동기화 유지하기
- 데이터 저장과 질의, 처리 요구사항을 모두 만족하는 단일 시스템은 없고 요구사항을 만족하기 위해 몇 가지 다른 기술의 조합이 필요하다. 
- 관련이 있거나 동일한 데이터가 여러 다른 장소에서 나타나기 떄문에 서로 동기화가 필수이다. 데이터 웨어하우스에서는 이 동기화 과정을 대개 ETL과정에서 수행한다. 이 과정은 일괄 처리다.
- 주기적으로 데이터베이스 전체를 덤프하는 작업이 너무 느리면 대안으로 이중 기록이 있다. 하지만 심각한 문제가 몇 가지 있다.
  - 동시성으로 타이밍이 교차하면 오류가 발생하지 않았음에도 서로 일치하지 않는다.
  - 이중 쓰기의 다른 문제는 한쪽 쓰기가 성공할 때 다른 쪽 쓰기는 실패할 수 있다는 점인데 이것은 내결함성 문제로 두 시스템 간 불일치가 발생하는 현상이 발생한다. 

##### 변경 데이터 캡처
- 데이터베이스에 기록하는 모든 데이터의 변화를 관찰해 다른 시스템으로 데이터를 복제할 수 있는 형태로 추출하는 과정으로 데이터가 기록되자마자 변경 내용을 스트림으로 제공할 수 있으면 특히 유용하다.
  - 예를들어, 변경 사항을 캡처해 검색 색인에 꾸준이 반영하면 데이터와 색인이 일치할 것이다.
- **변경 데이터 캡처의 구현**
  - 레코드 시스템에 발생하는 모든 변경 사항을 파생 데이터 시스템에 반영하는 것을 보장하는 메커니즘이다.
  - 로그 기반 메시지 브로커는 순서를 유지하기 때문에 원본 데이터베이스에서 변경 이벤트를 전송하기에 적합하다.
  - 데이터베이스 트리거를 사용하기도 하는데 이는 고장 나기 쉽고 성능 오버헤드가 상당하다.
  - 비동기 방식으로 동작하며 복제 지연의 몯느 문제가 발생하는 단점이 있다.
- **초기 스냅숏**
  - 데이터베이스에서 발생한 모든 변경 로그가 있다면 로그를 재현해서 데이터베이스의 전체 상태를 재구축할 수 있지만 디스크 공간이 많이 필요하고 재생하는 작업도 너무 오래 걸려서 로그를 적당히 잘라야 한다.
  - 전문 색인을 구축할 때 데이터베이스 복사본이 필요하지만 최근에 갱신하지 않은 항목은 로그에 없기 때문에 최근 변경 사항만 반영하는 것으로는 충분하지 않으므로 일관성 있는 스냅숏을 사용해야 한다.
- **로그 컴팩션**
  - 로그 히스토리의 양을 제한한다면 새로운 파생 데이터 시스템을 추가할 때마다 스냅숏을 만들어야 하지만 로그 컴팩션이라는 대안이 있다.
  - 저장 엔진이 주기적으로 같은 키의 로그 레코드를 찾아 중복을 제거하고 각 키에 대해 가장 최근에 갱신된 내용만 유지한다. 컴팩션과 병합 과정은 백그라운드로 실행된다. 
  - 로그 구조화 저장 엔진에서 특별한 널 값(툼스톤)으로 갱신하는 것은 키의 삭제를 의미하고 로그 컴팩션을 수행할 때 실제로 값을 제거한다. 그러나 툼스톤은 키를 덮어쓰거나 삭제하지 않는 한 영구적으로 유지한다.
  - CDC 시스템에서 모든 변경에 기본키가 포함되게 하고 키의 모든 갱신이 해당 키의 이전 값을 교체한다면 특정 키에 대해 최신 쓰기만 유지하면 충분하다.
  - 파생 데이터 시스템을 재구축할 때마다 새 소비자는 컴팩션된 로그 토픽의 오프셋 0부터 시작해서 순차적으로 모든 키를 스캔하면 최신 값이 존재하는 것이 보장된다.
- **변경 스트림용 API 지원**
  - 최근 데이터베이스들은 변경 스트림을 기본 인터페이스로서 지원하기 시작했다.
  
##### 이벤트 소싱
- 이벤트 소싱은 DDD 커뮤니티에서 개발한 기법으로 애플리케이션 상태 변화를 모두 변경 이벤트 로그로 저장하는데, CDC와 가장 큰 차이점은 추상화 레벨이 다르다는 점이다.
  - 변경 로그는 데이터베이스에서 저수준으로 추출한다. 데이터베이스에 기록하는 애플리케이션은 CDC가 실행 중인지 알 필요 없다.
  - 이벤트 소싱에서 애플리케이션 로직은 이벤트 로그에 기록된 불변 이벤트를 기반으로 명시적으로 구축한다. 이벤트 저장은 추가만 가능하고 갱신이나 삭제는 권장하지 않거나 금지한다. 애플리케이션 수준에서 발생한 일을 반영하게끔 설계됐다.
- 데이터 모델링에 쓸 수 있는 강력한 기법으로 애플리케이션에서 사용자 행동을 불변 이벤트로 기록하는 방식은 데이터베이스 보다 훨씬 유의미하다.
- 상황 파악이 쉽기 때문에 디버깅에 도움이 되고 애플리케이션 버그를 방지한다.
- 연대기 데이터 모델과 유사하고 이벤트 로그와 별 모양 스키마에서 발견한 사실 테이블 사이에도 유사점이 있다.
- **이벤트 로그에서 현재 상태 파생하기**
  - 사용자는 일반적으로 시스템의 현재 상태를 보기를 원해서 시스템에 기록한 데이터를 표현한 이벤트 로그를 가져와 사용자에게 보여주기에 적당한 애플리케이션 상태로 변환한다.
    - 변환 과정은 자유롭지만 다시 수행하더라도 동일한 상태를 만들어야하기 때문에 결정적 과정이어야 한다.
  - 로그 컴팩션은 다르게 처리해야 한다.
    - 레코드 갱신용 CDC 이벤트는 일반적으로 레코드의 가장 새로운 버전을 보유하므로 기본키의 현재 값은 전적으로 기본키의 가장 최신 이벤트로 결정된다.
    - 이벤트 소싱은 이벤트를 보다 상위 수준에서 모델링한다. 사용자의 행동 의도를 표현하기 때문에 뒤에 발생한 이벤트가 앞선 이벤트를 덮어쓰지 않아서 이벤트의 전체 히스토리가 필요해 로그 컴팩션이 불가능하다.
  - 이벤트 소싱을 사용하는 애플리케이션은 일반적으로 이벤트 로그에서 파생된 현재 상태의 스냅숏을 저장하는 매커니즘이 있기 때문에 전체 로그를 재처리할 필요는 없지만, 이것은 장애 발생 시 읽고 복구하는 성능을 높여주는 최적화에 불과하다.
- **명령과 이벤트**
  - 이벤트 소싱의 철학은 이벤트와 명령을 구분하는데 주의하는데, 사용자 요청이 처음 도착했을 때 이 요청은 명령이고 실패할 수도 있다.
    - 무결성이 검증되고 명령이 승인되면 명령은 지속성 있는 불변 이벤트가 된다.
  - 이벤트는 생성 시점에 사실이 되고 이벤트 스트림의 소비자는 이벤트를 거절하지 못한다. 따라서 명령의 유효성은 이벤트가 되기 전에 동기식으로 검증해야 한다.
  - 이벤트를 두개로 분할해서 가예약, 유효한 예약에 대한 확정으로 분할하면 비동기 처리로 유효성 검사를 할 수 있다.

##### 상태와 스트림 그리고 불변성
- 모든 변경 로그는 시간이 지남에 따라 바뀌는 상태를 나타낸다.
- 변경 로그를 지속성 있게 저장한다면 상태를 간단히 재생성할 수 있고 시스템을 거치는 데이터 흐름에 관해 추론하기 쉽다.
- **불변 이벤트의 장점**
  - 데이터베이스에 불변성을 이용하는 아이디어는 예를들면, 거래가 발생하면 거래 정보를 원장에 추가만 하는 방식으로 기록하는 것이고 실수가 발생해도 원장의 거래 내역을 지우거나 괴지 않고 보완하는 거래 내역을 추가한다.
  - 다른 시스템에도 유용한데, 데이터베이스에 잘못된 데이터를 기록했을 때 코드가 데이터를 덮어썼다면 복구하기 매우 어렵지만 추가만 하는 불변 이벤트 로그를 썼다면 문제 상황의 진단과 복구가 훨씬 쉽다.
  - 불변 이벤트는 현재 상태보다 훨씬 많은 정보를 포함하는데, 장바구니에 항목을 넣었다가 제거했다면 이벤트를 취소한 것에 불과하지만 분석가의 관점에서는 구매하려 했다가 하지 않았다는 것을 알 수 있는 유용한 정보이다.
- **동일한 이벤트 로그로 여러 가지 뷰 만들기**
  - 불변 이벤트 로그에서 가변 상태를 분리하면 동일한 이벤트 로그로 다른 여러 읽기 전용 뷰를 만들 수 있는 데 한 스트림이 여러 소비자를 가질 때와 동일한 방식으로 작동한다.
  - 기존 데이터를 새로운 방식으로 표현하는 새 기능을 추가하려면 이벤트 로그를 사용해 신규 기능용으로 분리한 읽기 최적화된 뷰를 구축할 수 있고 기존 시스템과 함께 운용이 가능하다.
  - 데이터를 쓰는 형식과 읽는 형식을 분리해 다양한 읽기 뷰를 허용한다면 상당한 유연성을 얻을 수 있는데 이를 명령과 질의 책임의 분리 (command query responsibility segregation, CQRS)라 부른다.
  - 데이터를 쓰기 최적화된 이벤트 로그에서 읽기 최적화된 애플리케이션 상태로 전환 가능하면 정규화와 비정규화에 관한 논쟁은 거의 의미가 없다.
- **동시성 제어**
  - 이벤트 소싱과 변경 데이터 캡처의 가장 큰 단점은 이벤트 로그의 소비가 대개 비동기로 이뤄진다는 점이다. 사용자가 록에 이벤트를 기록하고 이어서 로그에서 파생된 뷰를 읽어도 기록한 이벤트가 아직 읽기 뷰에 반영되지 않았을 가능성이 있다.
  - 읽기 뷰의 갱신과 로그에 이벤트를 추가하는 작업을 동기식으로 수행하는 방법이 있는데 트랜잭션에서 여러 쓰기를 원자적 단위로 결합해야 하므로 다른 시스템에 있다면 분산 트랜잭션이 필요하다.
  - 이벤트 로그로 현재 상태를 만들면 동시성 제어 측면이 단순해진다. 이베트 소싱을 사용하면 이벤트를 로그에 추가만 하면 되며 원자적으로 만들기 쉽다.
- **불변성의 한계**
  - 대부분 데이터를 추가하는 작업이고 갱신이나 삭제는 드물게 발생하는 작업부하는 불변으로 만들기 쉽지만, 상대적으로 작은 데이터셋에서 매우 빈번히 갱신과 삭제를 하는 작업부하는 불변 히스토리가 감당하기 힘들 정도로 커지거나 파편화 문제가 발생할 수 있고 컴팩션과 가비지 컬렉션의 성능 문제가 견고한 운영을 하는 데 큰 골칫거리가 되기도 한다.
  - 성능적인 이유 외에도 개인 정보나 데이터 보호법 등에 따라 관리상의 이유로 데이터를 삭제할 필요가 있는데, 히스토리를 새로 쓰고 문제가 되는 데이터를 처음부터 기록하지 않았던 것처럼 하는 방법이 있다.

#### 스트림 처리
- 스트림을 처리하는 방법에는 크게 세 가지 선택지가 있다.
  1. 이벤트에서 데이터를 꺼내 데이터베이스나 캐시, 검색 색인 또는 유사한 저장소 시스템에 기록하고 다른 클라이언트가 이 시스템에 해당 데이터를 질의한다.
  2. 이벤트를 사용자에게 직접 보낸다.
  3. 하나 이상의 입력 스트림을 처리해 하나 이상의 출력 스트림을 생산한다.
- 스트림을 처리하는 코드 조각을 연산자나 작업이라 부른다.
- 일괄 처리 작업과 가장 크게 다른 점은 스트림은 끝나지 않는다는 점이다.

##### 스트림 처리의 사용
- 특정 상황이 발생하면 조직에 경고를 해주는 모니터링 목적으로 오랜 기간 사용돼 왔지만, 시간이 흘러 다른 용도로 스트림 처리를 사용하는 사용자들이 나타나기 시작했다.
- **복잡한 이벤트 처리(complex event processing, CEP)**
  - CEP는 정규 표현식으로 문자열에서 특정 문자 패턴을 찾는 방식과 유사하게 스트림에서 특정 이벤트 패턴을 찾는 규칙을 규정할 수 있다.
  - 질의는 처리 엔진에 제출하고 처리 엔진은 입력 스트림을 소비해 필요한 매칭을 수행하는 상태 기계를 내부적으로 유지하다가 해당 매치를 발견하면 엔진은 감지한 이벤트 패턴의 세부 사항을 포함하는 복잡한 이벤트를 방출한다.
- **스트림 분석**
  - 대량의 이벤트를 집계하고 통계적 지표를 뽑는 것을 더 우선하고, 일반적으로 이런 통계는 고정된 시간 간격 기준으로 계산한다.
  - 스트림 분석 시스템은 집합 구성원 확인 용도의 블룸 필터, 원소 개수 추정 용도의 하이퍼로그로그, 다양한 백분위 추정 알고리즘 등을 사용하기도 한다.
- **구체화 뷰 유지하기**
  - 어떤 데이터셋에 대한 또 다른 뷰를 만들어 효율적으로 질의할 수 있게 하고 기반이 되는 데이터가 변경될 때마다 뷰를 갱신한다.
- **스트림 상에서 검색하기**
  - 전문 검색 질의와 같은 복잡한 기준을 기반으로 개별 이벤트를 검색해야 하는 경우
  - 질의를 먼저 저장하고 문서는 질의를 지나가면서 실행된다.
- **메시지 전달과 RPC**
  - 액터 모델 등에서 쓰이는 서비스 간 통신 메커니즘으로 사용할 수 있다. 

##### 시간에 관한 추론
- 많은 스트림 처리 프레임워크는 윈도우 시간을 결정할 때 처리하는 장비의 시스템 시계를 이용하는데 간단하지만 눈에 띌 정도로 처리가 지연되면 문제가 생긴다.
- **이벤트 시간 대 처리 시간**
  - 처리가 지연되는 데는 큐 대기, 네트워크 결함, 메시지 브로커나 처리자에서 경쟁을 유발하는 성능 문제, 스트림 소비자의 재시작, 결함에서 복구하는 도중이나 코드 상의 버그를 고친 후 과거 이벤트의 재처리 등의 이유가 있다.
  - 메시지가 지연되면 순서를 예측하지 못할 수도 있다.
- **준비 여부 인식**
  - 이벤트 시간 기준으로 윈도우를 정의할 때 까다로운 문제는 특정 윈도우에서 모든 이벤트가 도착했다거나 아직도 이벤트가 계속 들어오고 있는지를 확신할 수 없다는 점이다.
  - 윈도우를 이미 종료한 후에 도착한 낙오자 이벤트를 처리할 방법이 필요하다.
    1. 낙오자 이벤트를 무시한다.
    2. 수정 값을 발행한다.
- **어쨋든 어떤 시계를 사용할 것인가?**
  - 이벤트가 시스템의 여러 지점에 버퍼링됐을 때 이벤트에 타임스탬프를 할당하는 것은 더 어렵다.
    - 예를 들면 오프라인일 때는 로컬에 이벤트를 버퍼링하다가 인터넷 연결이 가능해지면 이벤트를 서버로 보낼 때 소비자는 이벤트를 극단적으로 지연된 낙오자 이벤트로 본다.
  - 이런 맥락에서 이벤트의 타임스탬프는 실제 사용자와 상호작용이 발생했던 실제 시각이어야 하지만 사용자가 제어하는 장비의 시계를 항상 신뢰하기는 어렵고, 이벤트를 서버에서 받은 시각이 좀 더 정확하지만 사용자와의 상호작용을 설명하기에는 의미가 부족하다.
  - 이벤트가 발생한 시간, 서버로 보낸 시간, 서버에서 이벤트를 받은 시간 세 가지 타임스탬프를 로그로 남기는 방법이 있다.
- **윈도우 유형**
  - 윈도우는 이벤트 수를 세거나 윈도우 내 평균값을 구하는 등 집계를 할 때 사용한다.
    - 텀플링 윈도우: 크기는 고정 길이고 모든 이벤트는 정확히 한 윈도우에 속한다.
    - 홉핑 윈도우: 고정 길이를 사용하지만 윈도우를 중첩할 수 있다.
    - 슬라이딩 윈도우: 각 시간 간격 사이에 발생한 모든 이벤트를 포함한다.
    - 세션 윈도우: 고정된 기간이 없고 짧은 시간동안 발생시킨 모든 이벤트를 그룹화해서 세션 윈도우를 정의한다.

##### 스트림 조인
- 스트림 상에서 새로운 이벤트가 언제든 나타날 수 있다는 사실은 스트림 상에서 수행하는 조인을 일괄 처리 작업에서 수행하는 조인보다 훨씬 어렵게 만든다.
- **스트림 스트림 조인(윈도우 조인)**
  - 스트림 처리자가 상태를 유지해야 하는데, 지난 시간에 발생한 모든 이벤트를 세션 ID로 색인한 후 이벤트가 발생할 때마다 해당 색이넹 추가하고 같은 세션 ID로 이미 도착한 다른 이벤트가 있는지 다른 색인을 확인해야 한다.
- **스트림 테이블 조인(스트림 강화)**
  - 사용자 활동 이벤트 집합과 사용자 프로필 데이터베이스를 조인하는 작업이 이에 속하며 데이터베이스의 정보로 활동 이벤트를 강화한다고 한다.
  - 데이터베이스에서 원격으로 질의하는 방법은 느리고 데이터베이스에 과부화를 줄 위험이 있다.
  - 스트림 처리자 내부에 데이터베이스 사본을 적재하는 것도 있는데, 데이터베이스 로컬 사본 용량이 작으면 메모리 내 해시 테이블에 넣는 것이 가능하고 색인을 로컬 디스크에 넣을 수도 있다.
  - 스트림 처리자가 사용하는 데이터베이스의 로컬 복사본을 최신 상태로 유지하는 것은 변경 데이터 캡처를 사용하면 해결 가능하다.
- **테이블 테이블 조인(구체화 뷰 유지)**
  - 트윗에서 사용자가 홈 타임라인을 볼 때 전송이 기록되는 받은 편지함과 같은 타임라인 캐시를 사용해 단일 조회로 타임라인 읽기를 가능하게 한다.
  - 스트림 처리자에서 이 캐시 유지를 구현하려면 트윗 이벤트 스트림(전송과 삭제)과 팔로우 관계 이벤트 스트림(팔로우와 언팔로우)이 필요하다.
  - 트윗과 팔로우, 두 테이블을 조인하는 질의에 대한 구체화 뷰를 유지해서 질의 결과의 캐시가 타임라인이 되며 조인 대상 테이블이 변할 때마다 갱신된다.
- **조인의 시간 의존성**
  - 세 가지 유형 모두 스트림 처리자가 하나의 조인 입력을 기반으로 한 특정 상태를 유지해야 하고 다른 조인 입력에서 온 메시지에 그 상태를 질의한다.
  - 복수 개의 스트림에 걸친 이벤트 순서가 결정되지 않으면 조인도 비결정적이다. 이것은 동일한 입력으로 같은 작업을 재수행하더라도 반드시 같은 결과를 얻지는 못한다는 의미다.
  - 데이터 웨어하우스에서는 천천히 변하는 차원이라 하는데, 흔히 조인되는 레코드의 특정 버전을 가리키는 데 유일한 식별자를 사용해 해결한다.
  - 이렇게 변경한 조인은 결정적지만 테이블에 있는 레코드의 모든 버전을 보유해야 하기 때문에 로그 컴팩션이 불가능하다.

##### 내결함성
- **마이크로 일괄 처리와 체크포인트**
  - 스트림을 작은 블록으로 나누고 각 블록을 소형 일괄 처리와 같이 다루는 방법인데 이 방법을 마이크로 일괄 처리라 한다.
  - 일괄 처리 크기가 작을수록 스케줄링과 코디네이션 비용이 커지고 클수록 스트림 처리의 결과를 보기까지 지연시간이 길어진다.
  - 일괄처리 크기와 같은 텀블링 윈도우를 암묵적으로 지원한다.
  - 스트림 연산자는 가장 최근 체크포인트에서 재시작하고 해당 체크포인트와 장애 발생 사이의 출력은 버린다.
  - 체크포인트는 메시지 스트림 내 배리어가 트리거하는데 마이크로 일괄 처리 사이의 경계와 비슷하지만 윈도우의 크기를 특정하지 않는다.
  - 출력이 스트림 처리자를 떠나자마자 스트림 처리 프레임워크는 실패한 일괄 처리 출력을 더 이상 지울 수 없기 때문에 실패한 태스크를 재시작하면 외부 부수효과가 두 번 발생한다.
- **원자적 커밋 재검토**
  - 처리가 성공했을 때만 모든 출력과 이벤트 처리의 부수 효과가 발생하게 한다.
- **멱등성**
  - 멱등 연산은 여러 번 수행하더라도 오직 한 번 수행한 것과 같은 효과를 내는 연산으로 여분 메타데이터로 연산을 멱등적으로 만들 수 있다.
    - 예를 들어 카프카로부터 소비할 때 단조 증가하는 오프셋을 외부 데이터베이스에 값을 기록할 때 함께 포함한다면 반복해서 같은 갱신이 수행되는 것을 막을 수 있다.
  - 멱등 연산은 정확히 한 번 시맨틱을 달성하는 데 적은 오버헤드만 드는 효율적인 방법이다.
- **실패 후에 상태 재구축하기**
  - 윈도우 집계나 조인용 테이블과 색인처럼 상태가 필요한 스트림 처리는 실패 후에도 해당 상태가 복구됨을 보장해야 한다.
  - 원격 데이터 저장소에 상태를 유지하고 복제하는 것은 한가지 방법이지만 느리다.
  - 스트림 처리자의 로컬에 상태를 유지하고 주기적으로 복제하는 것도 한가지 방법이다.
  - 입력 스트림을 사용해 재구축하는 경우엔 상태 복제가 필요없을 수도 있다.
  - 모든 트레이드오프는 깁나 인프라스트럭처의 성능 특성에 달려있다. 어떤 시스템은 디스크 접근 지연 시간보다 네트워크 지연이 더 짧고 네트워크 대역폭이 디스크 대역폭과 비슷할 수도 있다. 모든 상황을 만족하는 트레이드오프는 없다.


### 💡 느낀 점
- 로그 기반 메시징 시스템에서 소비자가 생산자를 따라갈 수 없어서 메시지가 유실될 수 있다고 했는데, 예전에 운영 오픈서치 로그가 몇번 유실된 경험이 있다. 아무래도 로그가 많아지면서 비슷한 현상이 발생하지 않았을까 생각이 든다.
- 불변 이벤트는 현재 상태보다 훨씬 많은 정보를 포함해서 분석가들이 인사이트를 얻는 데 용의하다고 한 부분에서, 우리도 서비스를 운영하는 입장에서 사소한 것 하나하나 로깅을 하는 데 그 이유가 분석가들이 인사이트를 얻어 서비스를 점진적으로 좋게 만들어 나가려고 하는 것이라 생각됐다.
- 스트림 처리가 특정 상황이 발생하면 조직에 경고를 해주는 모니터링 목적으로 사용돼왔다는 것을 보면서 최근에 실무에서 여러 서비스들에 대해 이상 조기감지를 위해 커스텀 매트릭과 그라파나, 슬랙 웹훅을 통해서 얼럿 시스템을 만들었던 게 떠올랐다. 그라파나도 데이터를 스트림으로 처리하면서 특정 상황을 판별해주는 것 같다.
- 로그를 찍는 이벤트를 감지해서 이벤트 로그가 잘 쌓이는지 감지하는 모니터링을 구축했었는데, 가끔씩 말도 안되는 이벤트가 일부 찍히는 경우가 있어서 이 경우가 어떤 경우인지 궁금했다. 근데, 오프라인 상태에서 버퍼링 중이었다가 온라인이 됐을 때 전송을 한다면 그런식으로 됐을 수도 있겠다는 생각이 들었다. (단순 로깅 이벤트라 그럴 확률은 적을 것 같긴 하다.)
- 마지막에 로컬 상태 대 원격 상태의 가치는 저장소와 네트워크 기술의 발전에 따라 얼마든지 바뀔 수 있다는 말이 인상 깊었다. 네트워크 기술이 발전해서 신뢰할 수 있는 네트워크를 구축할 수 있다면 지금까지 발생한 분산 시스템의 거의 모든 고민들을 없앨 수 있지 않을까 싶다.
