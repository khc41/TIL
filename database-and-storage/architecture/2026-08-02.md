## 📅 2026-08-02
### 📖 Tech blog: [How Discord Stores Trillions of Messages](https://discord.com/blog/how-discord-stores-trillions-of-messages)
#### ✏️ Summation
- Their Cassandra cluster exhibited serious performance issues that required increasing amounts of effort to just maintain, not improve.
- They found potential performance pitfall: a server with just a small group of friends tends to send orders of magnitude fewer messages than a server with hundreds of thousands of people.
- In Cassandra, reads are more expensive than writes. Lots of concurrent reads as users interact with servers can hotspot a partition, which we refer to imaginatively as a “hot partition”.
- Cluster maintenance tasks also frequently caused trouble. We were prone to falling behind on compactions, where Cassandra would compact SSTables on disk for more performant reads. Not only were our reads then more expensive, but we’d also see cascading latency as a node tried to compact.
- They struggled with Cassandra's GC. Although ScyllaDB is most definitely not void of issues, it is void of a garbage collector, since it’s written in C++ rather than Java.
- They placed a Rust API server between the database and the application. They resolved the hot partition problem by using request merging in Rust. (If a thread is already reading, new requests subscribe to the ongoing read.)
- They initially estimated the migration would take 3 months, but they reduced it to 9 days by extending an existing library. It reads the database by token range, creates checkpoints in local SQLite, and quickly pushes the data into ScyllaDB.
- In this way, they could abandon the complicated time-based approach and simply flip the switch all at once, migrating at speeds of up to 3.2 million messages per second.
- After migrating to ScyllaDB, they reduced the cluster from 177 Cassandra nodes to just 72, while increasing disk space from 4TB to 9TB per node.
- They reduced the p99 latency for fetching historical messages from 40-125ms to 15ms, and improved insertion latency from 5-70ms to 5ms.

#### 💡 Reflections
- Reading this sentence "Reads, however, need to query the memtable and potentially multiple SSTables (on-disk files), a more expensive operation.", I was reminded of Cassandra's WAL (Write-Ahead Logging) approach, where writes are cheaper than reads. This is because to find the latest data, you may need to check multiple SSTables if it's not in the memtable, which can be costly.
- I learned that read and write quorums for durability and consistency can be affected by hot partitions, impacting multiple nodes.
- Cassandra's GC pauses can severely impact production traffic. Taking a node out of rotation just to run compaction seems to cause a massive operational overhead.
